# F10: Candy Swap brief for Kiro

Candy Swap is built **in Kiro, by Kiro, from a spec Kiro writes** (PRD F10, D-10, D-37). This file is the prompt a person on the team pastes into Kiro, plus a checklist for afterwards. Nobody hand-edits Kiro's output: it is evidence for the write-up and a fixture for F01 (KI-16).

**Why the prompt says so little about quality:** D-10 forbids planted bugs (KI-04). So the prompt describes the product and the contract Poltergeist needs (URLs, port, scripts, seed users) and nothing else. Don't add hints in either direction. Ask for nothing about how robust it should be, and nothing about making it fragile. Let Kiro build it the way it normally would.

## 1. Set up

1. Open `fixtures/candy-swap/` (this repo) **as its own Kiro workspace**, so Kiro writes its spec to `fixtures/candy-swap/.kiro/specs/candy-swap/`. That's where `npm run summon` and `npm run candy:check` look.
2. The folder already holds `poltergeist.config.json`. It isn't Kiro's, so Kiro should leave it alone.
3. Start a new **Spec** session in Kiro (requirements → design → tasks) and paste the prompt below.

## 2. Prompt (paste as is)

```text
Create a spec for "Candy Swap", a small Halloween candy-trading web app.

What it does:
- People log in with a handle and a password. There is no sign-up page; users come from a seed script.
- The market lists candy that is up for grabs, each with a name and a quantity left. A logged-in user can claim one piece of a candy from the market, which moves it into their inventory.
- The inventory page shows the logged-in user's own candy and quantities.
- A user can propose a trade: offer some of their own candy to another user in exchange for some of that user's candy.
- The trades page lists a user's incoming and outgoing trades. The recipient can accept or decline an incoming trade. Accepting swaps the candy between the two inventories.
- Users can log out.

Pages (use exactly these URLs):
- /              landing page with a link to log in
- /login         login form (handle, password)
- /market        the market (logged in)
- /inventory     my candy (logged in)
- /trades        my incoming and outgoing trades (logged in)
- /trades/new    propose a trade (logged in)

Stack:
- Node 22+, TypeScript, ESM.
- Hono with server-side rendered JSX pages and plain HTML forms. Keep client-side JavaScript to a minimum.
- better-sqlite3, with the database file under data/ (gitignored).
- Serve on http://localhost:4000.
- A standalone npm package in this folder (its own package.json and lockfile).

Scripts in package.json:
- "dev": starts the server on port 4000.
- "db:reset": deletes and recreates the database from a fixed seed, then exits. It must finish in well under a second and produce exactly the same data every time (no random values, no current timestamps in seeded rows).
- "db:dump": prints every seeded table's rows as one JSON object to stdout, with rows in a stable order (for example by primary key), then exits.

Seed data:
- Users ghost1, ghost2, ghost3, ghost4, ghost5 and ghost6, all with the same demo password. Put that password in a committed .env.example as CANDY_SWAP_PASSWORD.
- About ten Halloween candies in the market with small quantities, and a few pieces already in some users' inventories so trades are possible straight away.

Keep the spec small: 6 to 8 requirements with about 25 acceptance criteria in total, in EARS format.

This folder already contains poltergeist.config.json. Leave that file unchanged.
```

Let Kiro run the whole flow: requirements, design, tasks, then implement the tasks. Accept its normal choices. If Kiro asks clarifying questions, answer them from the prompt only. Where the prompt is silent, say "your choice".

## 3. Afterwards (human checklist)

1. **Commit Kiro's output as is**, including `fixtures/candy-swap/.kiro/` (specs, steering, hooks), with a timestamped commit message. Don't tidy anything.
2. `npm --prefix fixtures/candy-swap install`
3. Put the demo password in Doppler (or `.env`) as `CANDY_SWAP_PASSWORD`.
4. `npm run candy:check`. This is F10's Done-when: the spec parses with no F01 warnings, it has 6–8 requirements and about 25 criteria, the config loads, and `db:reset` is < 1 s and deterministic. **Log each F01 warning as a KI-16 note** instead of editing the spec.
5. If `candy:check` is green, start `npm run --prefix fixtures/candy-swap dev` and run the follow-ups it prints (KI-30, then `doppler run -- npm run summon` for KI-34, KI-36 and KI-42). Record whatever Poltergeist finds in `docs/` with timestamps (D-10).
6. If Kiro picked different URLs than asked, update `fixtures/candy-swap/poltergeist.config.json` (ours, not Kiro's) to match, rather than changing the app.
